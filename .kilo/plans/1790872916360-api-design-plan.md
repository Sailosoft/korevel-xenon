# API Design Plan (task 6)

Module: `src/modules/bunny-dev/modules/api-design`.
Source: `tasks.yaml` lines 36–43.

## Goal

1. Row "Delete" becomes an icon button (with tooltip).
2. Operations bar gets a max height with virtual scrolling.
3. Add `@faker-js/faker`; the mock return object lets the user select which item to fake, and AI generation selects the fake item type too.

## Key files

- UI: `BDApiDesign.Component.tsx`, `BDApiMock.Component.tsx`
- Shared list/button: `../components/BDList.tsx`, `../components/BDButton.tsx`
- Types/builders: `BDApi.Types.ts`, `BDApi.Domain.ts`
- AI: `BDApiDesign.Server.ts`, `../agent-manager/BDGenerationPanel.tsx`

---

## T1 — Icon delete button

1. Extend `BDListAction<T>` (`BDList.tsx` lines 32–38) with `iconOnly?: boolean` and `tooltip?: string`.
2. In `BDList.tsx` row-action render (lines 314–334) and bulk-action render (lines 173–184): when `iconOnly`, render only the icon (`BDButton` with no children) and wrap in a tooltip.
   - Tooltip primitive does not exist in bunny-dev; use HeroUI `Tooltip` + `Tooltip.Content` (pattern: `src/modules/bunny/src/table/BunnyReactiveTable.tsx`) or `aria-label` + native `title`. Prefer a small shared `BDIconButton` wrapper for reuse across modules.
3. Update the api-design Delete action (`BDApiDesign.Component.tsx` lines 782–789) to `{ label: "Delete", icon: Trash2, variant: "danger", iconOnly: true, tooltip: "Delete operation", onSelect }`.
4. Default behavior unchanged for all other modules (opt-in only), so no visual regression elsewhere.

Acceptance: Delete renders as a lone trash icon with a hover/focus tooltip; other modules' actions unchanged.

## T2 — Virtualized operation bar

The "Operation bar" is the Operations `BDList<BDAPI>` panel (middle column), grid at `BDApiDesign.Component.tsx` line 680, list at lines 749–790.

1. Add an optional prop to `BDList` props interface (`BDList.tsx` lines 40–57), e.g. `virtual?: { height: number }`.
2. When `virtual` is set, render the rows with `TableVirtuoso` (from `react-virtuoso`, already a dependency) inside a fixed-height container:
   - Use `fixedHeaderContent` for the existing header row and `itemContent` for rows, reusing the current cell rendering.
   - Disable the pagination footer (lines 343–374) while virtualized; keep bulk-selection support.
   - Extract the current `<tr>` body markup into a shared row renderer used by both the table and virtual paths to avoid duplication.
3. Apply to the Operations list with `virtual={{ height: 480 }}` and add `className` max-height on the surrounding card so the panel scrolls internally.
4. Leave default list behavior (paginated table) untouched for other modules.

Note: `TableVirtuoso` renders outside `<table>` semantics; verify checkbox/selection columns and column widths align. If row complexity makes this risky, fall back to a div-based `Virtuoso` with a CSS-grid row using the same column widths.

Acceptance: Operations list has a bounded height; long lists scroll smoothly without pagination; selection still works.

## T3 — Faker with selectable fake item type

1. Install dependency: `bun add @faker-js/faker`.
2. Define fake item types in `BDApi.Types.ts`, e.g.
   ```
   export const BD_API_FAKE_TYPES = ["name","firstName","email","uuid","url","phone","company","date","number","boolean"] as const;
   export const BD_API_FAKE_TYPE_OPTIONS = ...
   export function fakeValue(fakeType?: string): unknown { /* switch → faker.*() */ }
   ```
3. Persist selection in the domain:
   - `BDApi.Domain.ts`: add `fakeType?: string` to `BDAPIProperty` (lines 75–88) and `BDAPIReturn` (lines 98–109); also to array item type if present.
4. Mock builders (`BDApi.Types.ts` lines 181–240): when `fakeType` is set use `fakeValue(fakeType)`; otherwise fall back to `example ?? sampleForType(type)`.
5. Mock UI (`BDApiMock.Component.tsx`):
   - Add a per-property "fake as" `select` (options from `BD_API_FAKE_TYPE_OPTIONS`) for request body/params and response fields; persist via the operation update path.
   - Add a "Regenerate" action that rebuilds request/response using faker and the selected types.
   - Options should only appear for properties whose type maps to a fakeable value (string/number/boolean/date).
6. AI generation:
   - `BDApiDesign.Server.ts` `API_DSL` (lines 40–173): add `fakeType` to property and return schemas with a description enumerating allowed values ("One of: name, email, uuid, url, … when type is string/number/boolean").
   - Normalizers (`normalizeProperty`, `normalizeReturnItem`, lines 175–248) parse/validate against `BD_API_FAKE_TYPES`; drop unknown values.
   - Draft types (`BDApi.Types.ts` lines 244–283) and apply mapping (`BDApiDesign.Component.tsx` `draftField` lines 74–82, `draftReturn` lines 85–99) thread `fakeType` through.
7. Optional AI input selector: add a "fake item type" default in the generation `extraFields` (`BDApiDesign.Component.tsx` lines 590–626) only if a document-wide default is desired; per-field selection is the primary requirement.

Acceptance: `@faker-js/faker` installed; mock responses use faker values for selected fake types; AI-generated operations carry a `fakeType` per field; changing the selection regenerates the mock.

## Risks

- Virtualizing the shared `BDList` table is the highest-risk change; keep it opt-in and share row markup.
- faker is large; import only the needed methods/`faker` entry to protect the client bundle.
- The AI DSL encodes enums as description strings (Helix schema limitation); validate values in normalizers.

## Validation

- `bun run build` and `npm run lint` pass.
- Delete is icon-only with tooltip; Operations panel scrolls with many operations.
- Select fake types in the mock, regenerate, confirm faker output; AI generate and verify `fakeType` persisted on properties/returns.
